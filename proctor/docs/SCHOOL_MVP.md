# Учебный MVP: простая настройка и наблюдаемые события

Следующая ревизия UI/desk-search и актуальная приёмка: [CASE3_ACCEPTANCE.md](CASE3_ACCEPTANCE.md). Дублирующие стрелки убраны; направления теперь под большим видео, не плашкой на нижних пикселях.

## Что изменено в текущей ревизии

- Одна основная кнопка **«Настроить взгляд · 10 с»**: пять целей, звук, обратный отсчёт. Начало явно выбирает пользователь. Отдельная кнопка обновления нейтрального центра — 2 с.
- Цели находятся в координатах всего окна, не в маленькой области камеры: центральная точка не сдвигается к левому превью. Переходные первые 0.4 с каждого шага исключаются. Движение головы более 7° относительно центральной позы не обучает «глазной» target. Нужны минимум шесть стабильных кадров; шум и неразличимые направления не объявляются успешными.
- Неполная настройка сохраняет проверенный центр, но явно перечисляет неразличённые направления. Для них остаются базовые пороги, а не придуманное измерение. Резкая смена основного лица аннулирует его персональный центр.
- На главном экране только наблюдение: крупные отдельные состояния головы и глаз, стрелки, телефон/присутствие, удержание и лента. 17 статусов PDF — во вкладке «Кейс №3», числа/пороги — в «Настройках».
- Читаемые глаза подсвечиваются рамками, центрами iris и стрелками в направлении GAZE. На камере есть отдельные русские HEAD/GAZE подписи. Невалидный gaze не получает выдуманную стрелку. Отзеркаливание относится к превью, не изменяет классификацию.
- Длительный DOWN: отдельный hold **3 с** (настраиваемый), отдельное событие `GAZE_DOWN`, счётчик и цвет после фактического достижения порога. Боковой взгляд по умолчанию 2 с. Исправлено несоответствие общей крутилки и реального DOWN hold. Временная нечитаемость/моргание до gap tolerance не сбрасывает таймер, длительный разрыв и стабильный CENTER сбрасывают.
- Во время настройки направления не расходуют cooldown для предупреждений. Телефон/присутствие продолжают проверяться. В exam изменение диагностических порогов заблокировано; повторная принятая настройка — по паролю экзаменатора.

## Частично перекрытый телефон

Нельзя гарантировать узнавание любого телефона, когда половина закрыта: YOLO может не дать ни одного кандидата. Не рисуем отсутствующий детект и не поднимаем confidence искусственно.

Реальные пути подтверждения:

1. Уверенные текущие детекты → лёгкий tracker → повторное подтверждение → hold.
2. Текущий слабый детект ≥ max(0.15, 0.65 × strong threshold), стабильная рамка минимум три наблюдения / 0.35 с и **свежая реально найденная рука** пересекает телефон. Hands теперь запускается и по слабому кандидату, а не только после confirmed phone: прежняя циклическая зависимость устранена.
3. Повторное согласие global + detail ROI с IoU >0.25, реальный near-strong score ≥ max(0.22, 0.9 × strong threshold), минимум четыре наблюдения / 0.7 с. Свежие near/dual свидетели истекают за 0.55 с. В этом пути также нужна **текущая** модельная рамка, не прогноз.
4. Уже уверенный track может кратко восстанавливаться по слабому наблюдению с strong anchor ≤0.8 с.

Cross-source дубликаты global/ROI объединяются до tracker. Support `hand+time` / `ROI+time` виден в overlay и runtime JSON. Повышение confidence сбрасывает прежние подтверждения и повышает нижнюю границу слабой ветки. Рука сама по себе не создаёт phone detection. Полное исчезновение телефона не сохраняет warning за счёт прогнозов.

## Производительность: что действительно измеряется

Latest-frame slots по одному снимку, нет очереди старых кадров. YOLO nano остаётся локальным; detail search дозирован, Hands работает только около текущих кандидатов. Слабый профиль ограничивает PyTorch одним потоком; обычный — максимум двумя. MediaPipe primary ROI и отдельный full-frame scan остаются разделены для второго лица.

Во вкладке настроек: реальные Camera FPS / worker Hz, возраст данных, пропущенные кадры, времена YOLO / tracker / face scan / mesh / pose / gaze / Hands / logic / UI, RSS и CPU **процесса**. CPU может превышать 100% при нескольких ядрах: это не общий процент компьютера. runtime сохраняет фактические holds, gaze gates и основания подтверждения телефона. Эти значения управляют/объясняют события, не являются оценкой «точности».

## Фактически выполнено в среде разработки

- Python 3.11 compile + технические регрессии: независимые пять gaze directions, HEAD, DOWN hold / короткое моргание / сброс в CENTER, отсутствие ложного phone от руки или прогноза, влияние confidence, отсутствие потраченного direction cooldown при настройке, GUI controls и 17 строк требований.
- Нативный запуск нового окна на повторяемом публичном портрете: оба CV worker, 2-секундный центр, 10-секундные пять целей, завершение/SQLite. Статический портрет не «следует» точкам: UI честно перечисляет все четыре неразличённых направления. Это не видеопроверка правильных LEFT/RIGHT/UP/DOWN.
- Нативные YOLO + Hands, COCO128 image `000000000395`: обычный телефон и две искусственные 50%-маски (слева / снизу). До исправления нижняя маска давала кандидата без подтверждения; после support-ветки — текущий подтверждённый phone, raw score около 0.24 сохранён. [Записи](benchmarks/phone-static-occlusion-probe.json). Это контрольный статический пример, не общий recall при реальном перекрытии рукой.
- Проверены также другие открытые COCO128 фотографии: есть пропуски маленьких/сложных телефонов. YOLO11n на этих примерах не устранил проблему, поэтому безоснованной смены модели/заявления «новая модель точнее» нет. Веса по умолчанию остаются nano-YOLOv8n.
- Qt отрендерил main / case / settings / calibration states; проверены размеры элементов и запуск. **Просмотр PNG недоступен из-за ошибки инструмента изображения; визуальная QA не объявляется пройденной.** Нужна проверка на целевом Windows/DPI.

Для воспроизведения частичного телефона (COCO128 заранее скачать с https://ultralytics.com/assets/coco128.zip):

```bash
python -m proctor.tools.phone_occlusion_probe --coco-root /path/to/coco128
```

Изображения и модели не загружаются этим инструментом и не отправляются наружу.

## Кейс №3: реализация не равна приёмке

| Пункт PDF | Что реализовано / видно | Оставшая проверка |
|---|---|---|
| Телефон в руке / перед экраном | YOLO, кандидаты/confirmed, gated Hands, PHONE_IN_HAND | Живые разные телефоны/чехлы/реальное перекрытие, не одна статичная маска |
| Поднятие телефона для фото | PHONE_LIFTED по движению и PHONE_RAISED по зоне лица | Размеченное видео подъёма/возврата; намерение «для фото» не доказывается |
| Наведение камеры телефона | PHONE_AIMED, hold, пометка «эвристика» | Направление объектива однозначно не восстанавливается обычной веб-камерой |
| Направление глаз и длительный DOWN / side | Per-eye iris, базис головы, персональные targets, отдельные HEAD/GAZE, hold/event/overlay | Реальное движение только глазами / только головой / сочетания, очки, освещение |
| Присутствие / второе лицо | Full-frame scan + primary mesh, NO_FACE / MULTI_FACE time gates | Несколько живых людей, фон/фото/свет; anti-spoofing не реализован |
| Alt+Tab, Ctrl+C/V, Win, PrtScn | Windows/admin/exam hooks + clipboard, статусы активен/выключен | Проверка Windows; не все привилегированные OS обходы подавляются |
| Переключение вкладок | Только управляемый `--embedded-test`, URL/navigation/window policy | В автономном CV браузера нет: строка явно не считает пункт активным |
| Посторонние окна/браузеры | Focus watchdog и настроенные новые процессы | Application-level MVP, не полный kiosk и не запрет всех уже запущенных программ |

**Не закрыта полная физическая приёмка всех 19 сценариев.** Для неё нужен локальный видеопрогон на целевом ноутбуке с временной разметкой действий и отдельная проверка Windows-защиты. Нет обещания безошибочного gaze/50% phone detection. Для устойчивого улучшения пропусков нужен набор реальных positive/negative webcam сцен и, вероятно, дообучение nano-модели — UI это не заменяет.

Это учебный MVP, а не готовая к массовому развёртыванию система: прежде чем использовать со студентами, определить согласие, сроки хранения кадров, доступ преподавателей и порядок ручной проверки событий. Событие взгляда не доказывает нарушение.
