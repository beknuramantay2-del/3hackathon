# Поиск лиц, защита экзамена и проверка качества

## Исправления

Общий FaceDetection переведён на full-range модель MediaPipe. Short-range вариант на контрольном кадре с двумя копиями портрета не нашёл лица; full-range нашёл два, а на одиночном портрете — одно. FaceMesh по-прежнему обрабатывает только основное лицо. Это нативная проверка изображений, не доказательство работы с двумя живыми людьми при любом свете.

YOLO проверяет названия настроенных классов при загрузке. Неподходящие веса не могут молча выдавать «телефона нет»: ошибка модели блокирует готовность. Порог предупреждения не занижен ради видимого результата. Телефон, едва выступающий над столом, всё ещё требует специальной проверки/данных; не добавлен фиктивный «детект по прямоугольнику».

Перед защищённым экзаменом проверяются также уже открытые запрещённые программы. Преподаватель должен закрыть их сам: preflight не уничтожает несохранённые данные. Во время экзамена проверяются все процессы; режим `close` применяется к настроенным запрещённым программам, а ошибка доступа отображается как неполная защита, не как успех.

Обязательные Alt+Tab, Ctrl+C/V, Win, PrtScn и переключение вкладок больше нельзя случайно убрать из списка hooks пустой настройкой. Дополнительно сочетания навигации, новых вкладок/окон, копирования и вставки перехватываются в самом WebEngine. Разрешены обычный ввод и выбор ответов. Выход экзаменатора сохранён.

Готовность экзамена проверяется не по одному флагу keyboard. Нужны активные hooks, работоспособная проверка процессов, владение фокусом и защита буфера. Потеря фокуса/защиты блокирует ввод и создаёт отдельное событие. При потере камеры или свежих результатов CV ввод также блокируется. Явная отправка ответов повторно проверяет эти условия, а не полагается только на отключённый виджет. Окончание времени завершает попытку штатно; просроченный интерфейс не включается повторно.

## Оптимизация

- Auto-профиль учитывает доступную CPU affinity и объём RAM, а не только общее число логических CPU хоста.
- При перегрузке общий YOLO-вход может снижаться до 320. Размер detail ROI сохраняется отдельно: уменьшение общего кадра не уменьшает автоматически масштаб поиска маленького телефона.
- После устойчивого восстановления бюджета разрешение постепенно возвращается к исходному, без превышения начального лимита.
- Latest-frame transport, ограниченные очереди, отдельные writers и один global + максимум один detail-проход сохранены. Новый общий поиск лиц не добавляет второго FaceMesh или второй камеры.

20-секундный CPU weak replay показал около **29.85 FPS камеры/preview** и **677.2 MB пикового RSS измеряемого процесса**. Это Linux sandbox и статичный портрет. В benchmark нет полной нагрузки WebEngine/школьных окон; показатели не означают точность CV, latency предупреждения или результат i5‑4200M. [Полные измерения и ограничения](benchmarks/case3-hardening-check.json).

## Проверка живых сценариев

Replay-evaluator теперь использует настоящие `MandatoryCalibration` 15+15 с и `EpisodePolicy` приложения. Старые обходы `center`/`none` исключены. Повышение жёлтого до красного остаётся одним episode ID. UNKNOWN учитывается как ошибка измерения при оценке направлений, а не выкидывается из знаменателя.

Для проверки запишите видео, начинающееся с настройки: 3 с прямо/влево/вправо/вверх/вниз головой, затем те же пять направлений только глазами с прямой головой. После 30 с — сценарии проверки. Разметку должен проверить человек по самому видео, не по выводам детектора.

```powershell
python -m proctor.tools.replay_evaluator --video acceptance.mp4 --gt acceptance.json --output data/acceptance-result.json
python -m proctor.tools.benchmark --video acceptance.mp4 --seconds 30 --perf weak --output data/benchmark.json
```

Формат разметки:

```json
{
  "events": [
    {"type": "GAZE_DOWN", "t_start": 38, "t_end": 41}
  ],
  "segments": [
    {"t_start": 35, "t_end": 41, "head": "CENTER", "gaze": "DOWN"}
  ]
}
```

В `events` указывается ожидаемое окно первого предупреждения, не начало физического движения: для отвода нужны 3 с удержания. В `segments` — фактическое направление на интервале. Время считается от начала видео; первые 30 с — калибровка, не оценочный экзамен. Offline replay не измеряет realtime задержку — для неё отдельный benchmark.

Проверьте в видео отдельно голову и глаза L/R/U/D, короткий и долгий отвод вниз/в стороны, телефон в руке/перед экраном/при поднятии, уход и второе лицо. Дополнительно нужны плохой свет, очки и края стола. Направление объектива телефона по одной картинке однозначно не устанавливается: PHONE_AIMED остаётся сигналом возможного наведения для ручной проверки.

## Windows

На целевом компьютере после успешного preflight/калибровки проверьте каждую комбинацию Alt+Tab, Ctrl+C, Ctrl+V, Win, PrtScn, Ctrl+Tab и попытку открыть внешний браузер. Проверьте возврат фокуса, блокировку ввода при ошибке защиты, парольный выход и штатное восстановление буфера после завершения. Сначала сохраните работу в других программах. Проверка регистрации hooks в тестах не заменяет физического нажатия клавиш.

**Все требования нельзя считать принятыми по одному числу unit-тестов.** Остаются целевая камера, частично скрытый телефон, реальное наведение объектива и физическая Windows-проверка. Полный OS kiosk и удалённый мониторинг класса не заявляются.
